# Lowering Architecture Refactor Scope

**Status:** Intake scope; implementation not started  
**Date:** 2026-07-26  
**Repository:** `/home/ubuntu/tinygrad-arkey`  
**Proposed branch:** `refactor/lowering-architecture`  
**Risk:** High if attempted as a rewrite; manageable as a sequence of behavior-preserving slices

## 1. Objective

Refactor tinygrad's lowering stack so that:

1. Each lowering pass has one clear owner, an explicit input/output IR contract, and a recorded order.
2. Scheduling policy is separated from AST/UOp transformation.
3. Reusable lowering primitives are centralized in core codegen instead of living in model-specific `extra/qk` modules.
4. Model-specific kernels, route policy, resource evidence, and benchmark artifacts are modular and do not duplicate admission logic.
5. The normal compiler path and custom-kernel path share typed geometry, resource, provenance, and observability contracts.
6. The refactor reduces architectural complexity without silently changing fusion, materialization, kernel identity, correctness, or performance.

This is an architecture refactor. It is **not** a request to redesign the UOp IR, rewrite the scheduler, or solve the unresolved 14B G5 performance defect in the same change.

## 2. Current architecture to preserve while refactoring

The current broad pipeline is:

```text
Tensor graph
  -> UOp graph
  -> schedule/rangeify.py and schedule/indexing.py
  -> schedule dependency linearization
  -> codegen/opt/postrange.py scheduler and optimizer
  -> codegen/late expansion, devectorization, reduction, composite, register allocation
  -> renderer/backend source or ISA
  -> runtime compiler and device launch
```

The principal implementation areas are:

- `tinygrad/uop/`: UOp IR, metadata, pattern matching, graph rewrites, semantic operation types.
- `tinygrad/schedule/rangeify.py`: realization map, range propagation, bufferization boundary, movement lowering, composite ownership.
- `tinygrad/schedule/indexing.py`: range assignment, indexing, staging/bufferization, scoped/composite source handling.
- `tinygrad/schedule/__init__.py`: kernel dependency graph and schedule linearization.
- `tinygrad/codegen/opt/postrange.py`: optimization selection and AST mutation after rangeification.
- `tinygrad/codegen/opt/`: optimization contracts, policy objects, pipeline/resource validation, heuristic and explicit options.
- `tinygrad/codegen/late/`: expansion, devectorization, reduction lowering, composite combination, register storage/allocation.
- `tinygrad/renderer/`: target source/ISA rendering and target-specific lowering.
- `tinygrad/runtime/`: compilation, executable caching, queue submission, allocation, profiling, and launch.

The custom attention path is a second lowering mechanism:

```text
model route
  -> tinygrad/llm/fused_attention.py or decode_routes.py
  -> Tensor.custom_kernel or custom UOp builder
  -> extra/qk kernel/spec modules
  -> captured/emitted source or UOps
  -> renderer/runtime
```

Important custom-path files include:

- `tinygrad/llm/fused_attention.py`
- `tinygrad/llm/flash_prefill_attention.py`
- `tinygrad/llm/decode_routes.py`
- `extra/qk/flash_kernels.py`
- `extra/qk/coalesced_load_lowering.py`
- `extra/qk/warp_reduce_lowering.py`
- `extra/qk/kernel_pipeline.py`
- `extra/qk/route_manifest.py`
- `extra/qk/decode/*`
- `extra/qk/prefill/*`

The refactor must preserve the current generated/autogenerated boundary. Do not edit or reorganize `tinygrad/runtime/autogen`, generated artifacts, captured binaries, or unrelated hardware support while executing this scope.

## 3. Architectural diagnosis

### 3.1 Two partially independent lowering stacks

The normal compiler owns scheduling and lowering for ordinary graphs. Custom attention kernels often bypass that path through `Tensor.custom_kernel` and model-specific builders. This is an intentional safety/performance mechanism, but the contracts are not shared strongly enough.

Consequences:

- A route can have a different materialization and contiguity behavior from an ordinary kernel.
- Resource capture and kernel identity are not uniform.
- A scheduler change can be evaluated against a custom path that does not use the same lowering passes.
- Fusion, register lifetime, and G5 geometry investigations require separate instrumentation.

### 3.2 Policy is duplicated across code and manifests

Geometry admission, route identity, promotion status, expected resources, and evidence paths are split among model routes, spec validators, manifests, and benchmark scripts. This creates drift risk.

### 3.3 Pass ownership is implicit

`rangeify.py`, `indexing.py`, and `postrange.py` each contain both policy and transformation logic. Attention/composite-specific behavior is interleaved with general lowering. The final graph does not expose a stable pass trace explaining which pass materialized, fused, or changed a producer.

### 3.4 Metadata/provenance is not consistently typed

Composite and scoped lowering currently carries some ownership through tags and ad hoc metadata. This is fragile across graph rewrites and makes it difficult to validate provenance at pass boundaries.

### 3.5 Reusable transformations are outside core codegen

Coalescing, warp reduction, and pipeline helpers in `extra/qk` contain reusable compiler logic but are organized as experiment/model code. This makes central capabilities look optional and encourages duplicate implementations.

### 3.6 Environment variables are an implicit lowering API

Kernel variants such as staging, split score, inline reduction, and coalescing are selected by environment variables inside builders. This harms reproducibility and makes compilation behavior depend on ambient process state rather than an explicit plan.

### 3.7 The live flash kernel builder is too monolithic

`extra/qk/flash_kernels.py` combines geometry, KV loading, staging, score reduction, softmax recurrence, PV update, output, quantization, RoPE, and experimental branches. A typed composition boundary is needed before further optimization.

## 4. Non-goals and safety boundaries

- Do not rewrite UOp or replace `PatternMatcher`.
- Do not redesign `Tensor` or autograd.
- Do not combine this work with the unresolved 14B G5 performance fix.
- Do not change route admission, default route selection, or kernel math in a refactor-only slice.
- Do not delete generated/autogenerated code.
- Do not migrate every historical benchmark before the lowering contracts exist.
- Do not move code solely to reduce LOC; each move must improve ownership, reuse, or observability.
- Do not make a custom kernel opaque to correctness/resource accounting merely because it bypasses the ordinary scheduler.

## 5. Target architecture

The intended shape is an incremental version of:

```text
Graph IR
  -> RealizationPlan
  -> RangePlan
  -> BufferPlan
  -> KernelDependencyPlan
  -> OptimizationPlan
  -> LoweringPasses
  -> BackendProgram
  -> RuntimeExecutable
```

Each boundary should expose a typed, serializable summary. The implementation may retain existing UOp structures internally; the first goal is explicit ownership and traceability, not a new IR.

Proposed logical ownership:

```text
schedule/realize.py       materialization and producer/consumer partition
schedule/rangeify.py      logical shape/index/range lowering only
schedule/bufferize.py     storage, lifetime, and staging decisions
schedule/scopes.py        composite/scoped-reduction ownership
schedule/dependencies.py  kernel dependency and linear order
codegen/plan.py           immutable optimization/resource plan
codegen/passes.py         ordered pass descriptors and trace hooks
codegen/opt/              reusable target-neutral optimization policies
codegen/late/             lowering from planned UOps to linearized operations
renderer/                 target syntax/ISA and backend-specific emission
runtime/                  compilation, caching, launch, and device control
llm/kernel_specs.py       typed model-kernel descriptors and admission
extra/qk/                 model-specific builders, captures, and evidence only
```

These are logical boundaries first. Do not create empty modules or perform broad file moves until the contracts are proven.

## 6. Workstreams and tasks

### Phase 0: Baseline and inventory

#### LR-000: Freeze the baseline

Record:

- source revision and dirty-tree state
- Python and backend versions
- canonical CPU correctness tests
- canonical AMD compile/source identity checks
- route selection and admission output
- resource summary: VGPR, SGPR, LDS, scratch, workgroup/grid
- representative fixed-depth decode and prefill timing
- generated program/source hashes for refactor-only comparisons

Acceptance:

- Baseline artifact is stored under `bench/` or `docs/artifacts/` with the exact command and environment.
- A refactor-only run can distinguish a changed source hash from a changed route or shape.
- The current G5 authority result remains preserved separately and is not used as a refactor pass/fail gate.

#### LR-001: Inventory pass boundaries

Create a machine-readable table of every graph rewrite and lowering pass, including:

- owner file/module
- input node forms
- output node forms
- traversal order
- mutable context fields
- metadata/tags read and written
- target/backend assumptions
- tests and current callers

Acceptance:

- The table covers `rangeify`, `indexing`, schedule linearization, `postrange`, all late passes, renderer entry points, and custom-kernel injection.
- No pass is moved until its input/output contract is recorded.

### Phase 1: Make lowering observable

#### LR-010: Introduce a lowering trace contract

Define a small immutable trace record containing:

- pass name and version
- input graph fingerprint
- output graph fingerprint
- node/op counts
- range/axis summary
- bufferization/materialization decisions
- optimization plan identifier
- target and feature flags
- warnings or rejected candidates

The trace must be opt-in and low overhead. It must not print silently in normal execution.

Acceptance:

- A representative fused elementwise/reduce graph produces a complete ordered trace.
- The trace identifies the pass that materializes or preserves a producer.
- The trace works in an isolated subprocess, not only in a parent process that does not own execution.
- Existing program output and default cache behavior are unchanged when tracing is disabled.

#### LR-011: Add pass invariant checks

For each pass, add cheap debug-only assertions for:

- valid UOp types
- range ownership and closure
- buffer/stage address-space invariants
- composite/scoped provenance
- launch-dimension consistency
- metadata preservation rules

Acceptance:

- Invalid hand-constructed graphs fail at the pass that introduced the invalid state.
- Assertions are disabled by default and do not alter generated code.

### Phase 2: Type the contracts crossing passes

#### LR-020: Replace stringly provenance with typed metadata

Define typed records for at least:

- composite owner/scope
- reduce slot and logical axis ownership
- memory semantic role
- materialization reason
- custom-kernel parameter slot ownership

Maintain a compatibility reader for existing metadata while migrations are staged.

Acceptance:

- Existing composite and scoped-reduction tests pass without changing emitted math.
- A pass cannot silently attach composite metadata to an unrelated node.
- Trace output identifies the owner and consumer of a staged value.

#### LR-021: Unify resource and pipeline contracts

Extend the existing typed policy work in `tinygrad/codegen/opt/compiler_policies.py` and `kernel_pipeline.py` so that normal and custom kernels use the same representation for:

- storage kind and slot count
- wait/barrier policy
- logical stages
- expected and final resources
- supported target/capability

Avoid claiming final VGPR/SGPR counts from host estimates.

Acceptance:

- Custom-kernel resource capture emits the same schema as ordinary compiled programs.
- A missing or stale resource field fails closed.

### Phase 3: Separate scheduling decisions from transformations

#### LR-030: Introduce `RealizationPlan`

Extract the decision result from the current realization logic without initially moving behavior. The plan should state:

- which producers materialize
- which consumers retain producer ownership
- why a buffer is forced
- which composite/scoped owners are active

Acceptance:

- The old and planned paths produce identical schedules on the baseline corpus.
- The plan explains the producer/reduce case that motivated this refactor.

#### LR-031: Introduce `OptimizationPlan`

Separate optimizer choice from AST mutation. The plan must represent:

- axis types and mappings
- upcast/unroll/local/thread/group decisions
- coalescing width
- staging/pipeline policy
- reduction mode
- resource budget
- explicit target capabilities

The existing `Opt` list may be retained as a compatibility encoding during migration.

Acceptance:

- Applying an `OptimizationPlan` twice is rejected or proven idempotent.
- A plan can be serialized and replayed in a clean subprocess.
- Environment variables are parsed once into a plan and are not read deep inside transformations.

#### LR-032: Add an ordered pass registry

Create pass descriptors with:

- stable name
- declared input/output phase
- required metadata
- provided metadata
- ordering constraints
- target capability predicate
- trace hook

The registry must make the actual pass order visible without changing it initially.

Acceptance:

- The current default pipeline can be printed as an ordered list.
- Reordering a pass with unsatisfied dependencies fails before code generation.

### Phase 4: Split schedule ownership incrementally

#### LR-040: Isolate realization decisions

Move only the realization-map calculation into a focused module. Preserve the existing graph rewrite implementation until parity is established.

#### LR-041: Isolate range propagation

Keep movement-op lowering and range propagation separate from storage allocation. The result should be a `RangePlan` or equivalent context with no device allocation side effects.

#### LR-042: Isolate bufferization and staging

Move `STAGE`, `BUFFERIZE`, local/register storage decisions, and lifetime closure behind a typed buffer plan. Keep address-space lowering backend-neutral until renderer capability is consulted.

#### LR-043: Isolate composite/scoped lowering

Make composite ownership an explicit lowering extension rather than scattered special cases. A composite extension should declare:

- producer slice it owns
- reduction axis and state shape
- allowed storage/lane representation
- required synchronization
- fallback behavior

Acceptance for Phase 4:

- Existing schedule fingerprints are unchanged for ordinary elementwise, reduce, matmul, and attention graphs.
- Composite tests still exercise the same ownership contract.
- No pass reaches into another pass's mutable context without a declared interface.

### Phase 5: Centralize reusable codegen primitives

#### LR-050: Promote reusable QK lowering passes

Evaluate and, if generic, move or re-export these from core codegen:

- `extra/qk/coalesced_load_lowering.py`
- `extra/qk/warp_reduce_lowering.py`
- reusable parts of `extra/qk/kernel_pipeline.py`
- target capability checks used by those passes

Model-specific geometry must remain in `extra/qk`.

Acceptance:

- Core codegen owns the reusable pass implementation.
- `extra/qk` imports the core pass rather than maintaining a fork.
- The pass has CPU/compile-only tests and a positive control proving it actually changed the intended AST/code object.

#### LR-051: Replace ambient flags with explicit plans

Convert decode/prefill lowering flags into typed plan fields. Keep CLI/environment adapters at the entry point only.

Required fields include, as applicable:

- staging mode
- reduction mode
- score split mode
- coalescing width
- quantization and RoPE load transforms
- vectorization policy

Acceptance:

- The same plan produces the same source fingerprint in isolated runs.
- A rejected plan fails before launching a GPU kernel.

### Phase 6: Modularize custom kernel specifications

#### LR-060: Define a common `KernelSpec` contract

The descriptor should own or reference:

- stable route/variant identity
- target
- geometry
- input/output ABI
- lowering plan
- resource contract
- correctness evidence
- performance evidence
- admission predicate
- emitter/builder

The manifest should be generated from these descriptors, not manually duplicated.

#### LR-061: Unify prefill and decode admission

Make `tinygrad/llm/fused_attention.py`, `flash_prefill_attention.py`, `decode_routes.py`, and `extra/qk/route_manifest.py` consume the same descriptor/gate representation.

Acceptance:

- One geometry change updates runtime admission, manifest census, and benchmark metadata.
- Unsupported shapes fail loudly and do not fall through to a falsely named route.

#### LR-062: Introduce a first-class custom-kernel boundary

Keep custom kernels opaque to ordinary fusion where required, but require the same typed metadata and trace records as compiled kernels:

- source/ABI identity
- buffer roles
- shape and launch dimensions
- resource capture
- correctness gate
- route identity

### Phase 7: Decompose the live flash builder

#### LR-070: Split `extra/qk/flash_kernels.py` by semantic stage

Target modules:

```text
extra/qk/decode/geometry.py
extra/qk/decode/kv_loader.py
extra/qk/decode/staging.py
extra/qk/decode/score.py
extra/qk/decode/softmax.py
extra/qk/decode/pv_update.py
extra/qk/decode/output.py
```

The top-level builder should compose these stages from a `DecodeKernelPlan`. Do not change arithmetic or axis ownership during this phase.

Acceptance:

- Default `KV_BOTH` source and resource fingerprints remain unchanged, or differences are explicitly explained and approved.
- Quantized KV and RoPE-at-read paths retain their existing ABI and correctness gates.
- G4 and G5 route identities remain distinct.

#### LR-071: Add compile-only variant matrix

For every plan variant, capture:

- source/code-object hash
- workgroup/grid
- VGPR/SGPR/LDS/scratch
- global load/store count where available
- positive source/name match count

No GPU timing is allowed until the variant passes the compile-only contract.

### Phase 8: Retire duplicated and dead structure

#### LR-080: Classify legacy paths

Classify each path as `active`, `fallback`, `research`, `retired`, or `generated`. The classification must be consumed by route census and documentation.

#### LR-081: Remove only proven dead code

Deletion requires:

- no runtime/import/test references
- no authority/evidence citation
- replacement or ledger entry for any historical result
- a positive search proving the deletion target was not silently used

Do not delete historical raw artifacts until their conclusions are represented in a benchmark ledger.

## 7. Validation matrix

### Static and CPU gates

- UOp construction and graph-rewrite unit tests
- rangeify/indexing tests
- schedule dependency tests
- optimizer plan round-trip tests
- metadata/provenance validation tests
- renderer compile-only tests
- custom-kernel ABI/slot tests

### Backend gates

- CPU execution parity
- AMD compile-only source/resource capture
- AMD correctness with positive controls
- isolated-subprocess execution, because parent-process probes do not observe worker kernels
- no silent false-negative instrumentation

### Performance gates

Use the existing fixed-depth authorities, not ad hoc generate-window timing:

- decode authority at fixed contexts
- prefill authority at canonical shapes
- exact route identity and source match count
- 3 warmups and repeated synchronized samples
- power/clock state recorded before and after

Refactor-only acceptance target:

- no correctness regression
- no route/admission change
- no unexplained source or ABI change
- no more than 2% median regression on canonical authority runs, unless the change intentionally alters code generation and is separately approved
- no unexplained resource increase greater than 5%

The unresolved G5 depth cliff is tracked separately. A refactor may improve or worsen it, but it cannot claim to solve it without a dedicated candidate gate.

## 8. Parallel low-agent task packets

Low-reasoning agents may execute these independently after LR-000:

1. **Inventory agent:** build the pass/metadata/caller table; no production edits.
2. **Trace agent:** add a disabled-by-default pass trace and tests; no pass reordering.
3. **Contract agent:** draft typed metadata records and compatibility readers.
4. **Route agent:** model existing route/spec/manifest duplication and propose one descriptor schema.
5. **Core-pass agent:** compile-only evaluation of moving coalescing/warp helpers into core; no behavior change.
6. **Flash decomposition agent:** produce module boundaries and import graph; no arithmetic edits.
7. **Validation agent:** add source/resource fingerprint and positive-control tests.
8. **Ledger agent:** classify benchmark artifacts and record supersession; do not delete raw evidence.

Agents must not:

- modify generated/autogenerated files
- change default route selection
- run unbounded GPU sweeps
- delete probes without a positive-control-backed replacement
- combine multiple architectural slices in one patch

## 9. Branch and commit strategy

Use a dedicated branch named `refactor/lowering-architecture` from a recorded clean baseline. Keep commits small and independently revertible:

1. baseline and trace infrastructure
2. typed metadata contracts
3. optimization-plan contract
4. schedule boundary extraction
5. reusable pass promotion
6. kernel-spec/route unification
7. flash builder decomposition
8. dead-path cleanup and ledger update

Each commit must state whether generated source, route identity, ABI, or resource fingerprints changed. Refactor commits should not mix formatting-only edits or unrelated benchmark cleanup.

## 10. Rollback and stop rules

Stop the current slice and revert it if any of the following occurs:

- a pass-order change cannot be explained by the trace
- a source/ABI change appears in a refactor-only commit without a deliberate plan change
- a positive-control probe returns zero kernels or zero expected matches
- correctness differs without a documented intended semantic change
- a GPU fault/reset occurs during a new candidate experiment
- benchmark results are collected with the wrong authority or stale boot/power state
- an agent cannot identify the owner of a metadata field after the proposed move

Do not continue layering new abstractions over a failed contract. Return to the last green slice and revise the boundary.

## 11. Definition of done

This scope is complete only when:

- the default lowering pipeline has an explicit, inspectable pass order;
- realization, range, buffer, optimization, and backend decisions have distinct owners;
- provenance and resource contracts are typed and validated;
- reusable QK lowering primitives are centralized or explicitly justified as target-specific;
- route/spec/manifest admission is derived from one descriptor model;
- custom kernels participate in the same evidence and trace schema;
- the live flash builder is decomposed without unapproved math or ABI changes;
- canonical correctness and performance gates pass;
- dead paths and benchmark artifacts are classified, with deletions backed by a ledger;
- no generated/autogenerated code was hand-edited;
- the unresolved G5 performance question is either unchanged and separately scoped or solved by its own evidence-qualified candidate.

## 12. Expected difficulty

This is a **high-difficulty but tractable** refactor. The difficult part is not moving files; it is preserving hidden graph-rewrite invariants, metadata ownership, generated-kernel identity, and backend resource behavior.

The safe strategy is to add contracts and traces first, then extract one boundary at a time. A full rewrite of `rangeify` or the scheduler would be unnecessarily risky. The highest-value first slice is LR-010 plus LR-031: an explicit lowering trace and serializable optimization plan. Those two pieces make every later structural move measurable and reversible.
